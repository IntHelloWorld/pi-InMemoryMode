2026-10-18 外部修改修订：命令收敛为 `/inmem sync` 和 `/inmem recover`。自动比较只在新任务开始前、托管文件修改提交前和整个任务结束前执行。同一任务只有首次模型请求比较，后续请求不重复扫描。首次请求前发现差异时保存指令并等待选择；执行中发现差异时结束旧任务并标记未完成。sync 接纳外部修改并记录消息，recover 撤销外部修改但保留助手成功修改；两个命令均等待新指令，不自动续跑。任务开始前的回退交给 `/tree`。

Pi In Memory Mode 面向需要持续生成和修改文档的工作。插件将指定目录内的文件内容组织成一条工作区快照消息，放在模型上下文靠后的位置。工作内存和磁盘文件随成功的工具修改实时更新；同一个用户任务内，上下文中的文件快照保持冻结，下一条用户指令开始处理时再以最新工作状态替换。

第一版完整保留原始聊天和工具记录，使用 Pi 的 `/tree` 管理修改分支。下一条用户指令开始处理时，在模型上下文中省略上一已完成任务工具调用中的重复正文，并以最新工作状态替换文件快照。回到历史节点时，从原始记录恢复对应的聊天上下文、文件内容和投影状态；继续输入后形成新分支，原分支仍可切回。

## 已确定的范围

| 事项 | 第一版决定 |
| --- | --- |
| 文件进入上下文 | 指定目录内纳入管理的文件全文进入上下文 |
| 会话类别 | 首次聊天前确定，InMemory 专用会话与普通会话不能互相转换 |
| 消息组织 | 所有托管文件合成一条逻辑上可变的工作区快照消息 |
| 消息位置 | 放在本次真实用户指令之前，位于已有聊天记录之后 |
| 修改方式 | agent 主要通过工具修改文件，成功后实时更新工作内存和磁盘 |
| 快照更新时机 | 同一个用户任务内冻结上下文快照，下一条用户指令开始处理时再替换 |

| 工具消息压缩 | 下一条用户指令开始处理时，在模型上下文中省略上一已完成任务的 `edit` 旧文本、新文本及 `write` 正文 |

| 要求整理 | 第一版不做自动提取、整理或替换历史要求 |
| 分支管理 | 使用同一会话内的 `/tree`，第一版不以 `/fork` 作为版本管理入口 |
| 回退语义 | 同时恢复目标节点的文件、上下文和插件状态 |

| 原始记录用途 | 保留完整工具参数和结果，用于查看历史及 `/tree` 恢复，不用精简投影覆盖原始记录 |
| 文档版本 | 后台保存不可变版本；请求中只保留一份任务基线全文，后续变化由工具记录表达 |

“目录内所有文件”指纳入管理且能作为文本处理的文件。具体文本格式、排除规则和上下文容量限制需要在实现前确定，不能将二进制文件直接当作正文注入。

## 需要解决的问题

普通文档编辑流程常在多次读取结果、修改参数和聊天草稿中重复携带正文。修改次数增加后，模型需要重新定位当前版本，并区分仍有效的内容和已经过时的内容。

第一版让任务开始时的文件全文直接存在于请求上下文中，减少为获得编辑起点而进行的重复读取。任务期间，冻结的全文基线和后续成功工具记录共同表达当前作品；需要核对最新正文时，读取工具访问实时工作内存。

该模式不保证上下文恒定大小。普通聊天和精简后的工具操作记录仍会增长；如果 agent 在聊天中输出整篇正文，那份正文不属于本版工具参数压缩范围。`/tree` 排除已经放弃的路线，工具消息压缩减少已完成任务的重复正文，两者都不会删除原始历史。

## 状态模型

### 当前状态与历史状态

插件区分以下状态：

1. **活动会话路径**：Pi 从当前节点向根节点追溯得到的历史。
2. **当前工作区**：内存中可编辑的文件内容，以及同步保存的磁盘文件；随成功编辑实时更新。
3. **任务基线**：用户指令开始处理时捕获的不可变文件状态。
4. **请求快照消息**：由任务基线生成的文件全文；在本任务的多次模型调用之间保持内容和位置不变。
5. **工具历史投影**：根据原始工具消息生成的模型输入视图；只在新用户任务开始时确定上一已完成任务的正文省略范围，并在本任务内保持稳定。

“用户任务”是一条用户指令实际开始处理后触发的一段 agent 工作，可能包含多次模型调用和多次工具编辑。单次模型调用或一次工具执行都不构成新的用户任务。

任务开始时，任务基线与当前工作区相同，并确定适用于该任务的工具历史投影。成功编辑后，当前工作区指向新的不可变文件快照，任务基线和已有正文省略规则保持不变。历史检查点记录会话节点、实时工作区快照、挂载配置，以及恢复任务所需的基线引用、任务边界和投影状态。

```text
会话节点或任务边界
    └─ 检查点引用
         ├─ 工作区快照 ID        随成功编辑更新
         ├─ 任务基线快照 ID      同一用户任务内冻结
         ├─ 任务 ID 和指令锚点
         ├─ 工具历史投影状态     仅省略已完成任务的重复正文
         └─ 挂载配置
              ├─ 根目录
              └─ 文件纳入规则

工作区快照
    └─ 文件清单：相对路径 → 内容对象
```

“可变消息”按用户任务更新。恢复状态不能只保存一个被反复覆盖的正文对象，也不能只保存实时工作区而丢失任务基线，否则旧分支或未完成任务可能错误地使用新版正文。

### 一致性条件

只有满足以下条件时，才允许 agent 继续使用托管工作区：

- 内存文件内容与当前工作区快照一致。
- 托管磁盘文件与当前工作区快照一致。
- 请求中的全文由当前任务基线生成，同一任务内不因工具修改而变化。
- 基线之后保留足够的成功工具调用及结果，使模型能够理解当前工作状态。
- 工作区快照、任务基线和修改记录属于同一活动会话路径，而不是其他分支的最新状态。
- 当前任务的工具参数保持完整；只有最终文件状态已由新任务基线承接的已完成任务，才可按规则省略重复正文。
- 原始会话记录不受投影压缩影响，省略范围可根据对应分支和任务恢复。

任务执行期间，工作区快照与任务基线可以不同。两者通过该任务已成功的修改关联，不要求请求中的全文始终等于磁盘文件。

失败、中断或恢复操作不能留下跨分支错配的状态继续运行，也不能让基线与工作区之间出现缺少成功修改记录的差异。

## 模型上下文组织

### 单条工作区快照消息

每次模型请求按下面的逻辑顺序组织：

```text
系统规则和工具声明
活动路径上此前的聊天记录   已完成任务的工具重复正文按投影规则省略
工作区快照消息             本次任务开始时的文件全文，任务内冻结
本次真实用户指令
本次任务已经产生的 assistant 消息和工具调用结果   持续追加
```

同一次用户任务中，快照消息的正文、位置和已有工具历史投影均保持不变。每次成功编辑只更新工作内存、磁盘和恢复记录，后续模型调用在末尾追加完整工具调用与结果。任务结束时保存最终工作状态和检查点；下一条用户指令实际开始处理时，捕获最新工作状态作为新基线，同步确定上一已完成任务的工具正文省略范围，并将唯一的快照消息放到新指令之前。

```text
任务开始：工作区 D0，基线 D0
请求 1：历史 + 全文 D0 + 用户指令 U1
修改 1 成功：工作区 D1，基线仍为 D0
请求 2：历史 + 全文 D0 + 用户指令 U1 + 修改 1 及成功结果
修改 2 成功：工作区 D2，基线仍为 D0
请求 3：历史 + 全文 D0 + 用户指令 U1 + 修改 1 及成功结果 + 修改 2 及成功结果
任务结束：检查点保存最终工作区 D2
下一条指令开始：基线更新为 D2，上一任务的 edit/write 重复正文在投影中省略
新任务请求：历史操作的精简投影 + 全文 D2 + 用户指令 U2
```

插入位置根据真实用户任务的边界识别，不能仅凭转换后的消息角色判断，也不能插入尚未配对的工具调用与结果之间。连续输入和任务中追加指令的具体边界处理列为实现验证项。

快照内部按固定的相对路径顺序排列，包含路径和任务开始时的完整正文，并用稳定的文件边界区分内容。说明头明确其基线语义。示意格式如下，具体编码尚未确定：

```text
本次任务开始时的文件状态
后续成功编辑以工具调用及结果为准，读取工具返回最新工作内容。

文件 outline.md
正文……

文件 chapter-1.md
正文……
```

快照内容作为文件数据呈现，具有明确边界。版本指纹、检查点引用等管理信息保存在插件状态中；除非影响本次编辑判断，不在正文前加入时间戳或频繁变化的元数据。

### 请求构建与会话持久化

插件在新用户任务开始时捕获基线并确定工具历史投影，在每次请求前使用相同规则生成模型输入。同一任务不能每次都从最新工作区重新生成全文，也不能提前压缩本任务正在使用的工具参数。逻辑上的原位更新不要求模型服务提供特殊的“可变消息”类型，也不要求把每份文件全文都作为新的聊天消息追加。

持久层保存完整原始会话、检查点、任务基线引用、不可变正文和工具历史投影状态。模型上下文只注入本任务的一份基线快照，不能把工作区的中间版本或全部历史快照注入会话。精简后的工具消息是派生视图，不能写回覆盖原始会话。

恢复到历史节点后，从完整原始记录按该节点的活动路径恢复聊天、文件和投影状态。未完成任务保留原冻结基线和完整工具记录；不能套用未来任务已经省略参数的视图。从恢复点收到新指令时，创建新任务并以恢复后的工作区建立新基线；只有确已完成的任务才参与正文省略。这里恢复的是本地可重建的上下文，不是服务端内部的模型缓存或隐藏推理状态。

### 已完成任务的工具消息压缩

压缩发生在下一条用户指令实际开始处理时，处理范围是上一整个已完成用户任务，不是单次模型调用或一次工具执行。先确认最终工作状态已经进入新任务的文件基线，再生成工具历史投影；若建立新基线失败，就不能先发布省略正文的视图。

第一版针对本插件托管文件的 `edit` 和 `write` 调用采用确定性字段规则：

| 工具 | 在模型投影中省略 | 继续保留 |
| --- | --- | --- |
| `edit` | `edits[].oldText` 和 `edits[].newText` 的正文 | 路径、工具名称、调用 ID、非正文参数、对应执行状态和版本引用 |
| `write` | `content` 中的文件正文 | 路径、工具名称、调用 ID、非正文参数、对应执行状态和版本引用 |

省略的字段使用明确的历史正文省略标记，并关联原始条目或文件版本。标记只表示旧调用参数在当前请求视图中被省略，不代表工具当时写入了这段标记。工具调用与结果保持配对，工具名称、调用 ID 和必要的消息结构不变。

如果对应工具结果也包含同一份冗余正文，可以配套省略该正文，保留执行状态和其他有用信息。第一版不自动扩展到任意工具、`bash` 输出、用户要求或 assistant 的普通聊天文字。一个 assistant 消息同时包含多个工具调用和普通文字时，只处理符合条件的正文参数。

允许省略需要同时满足：

1. 来源任务已结束，操作结果已确认，不存在需要继续执行的工具调用。
2. 目标属于当前托管工作区，其最终状态已由新任务基线承接；文件后续被修改或删除时，以最终文件清单为准，不要求每个历史正文都与当前全文相同。
3. 完整原始参数、工具结果和文件版本仍可读取。
4. 省略后仍能构造合法的模型请求，且不会删除解释当前任务变化所必需的信息。

当前任务的工具调用保持完整。失败、中断或归属不明的任务，以及新基线未覆盖的目录外文件，第一版保守保留原内容，不按“已经完成并承接”处理。

示意如下，省略标记的实际编码和模型协议适配仍需验证：

```text
完整原始会话
  assistant 调用 write：路径 chapter.md，content 为完整正文 D1
  工具结果：成功
  assistant 调用 edit：完整 oldText 和 newText
  工具结果：成功，最终文件为 D2

下一用户任务的模型输入
  历史 write 调用：保留路径和调用 ID，正文标记为已省略
  历史结果：成功
  历史 edit 调用：保留路径和调用 ID，旧文本和新文本标记为已省略
  历史结果：成功
  文件基线：完整正文 D2
  新用户指令
```

省略范围一经确定，在新任务内保持稳定；再下一任务开始时，可在此前精简视图基础上处理刚完成任务的正文。所有视图均可从原始记录及对应投影状态重建，不能通过反复原地删除原始消息来累积压缩。

### 缓存策略

任务内部冻结快照和已有工具历史投影，使后续请求主要通过追加消息增长，稳定前缀可以包含文件基线、用户指令和先前的工具记录。任务之间替换快照时，靠后的位置有助于保护更早的聊天前缀。压缩上一任务的正文参数还会从该任务最早被改写的位置开始影响前缀，因此不能承诺此前所有聊天都命中缓存。实际效果还取决于模型、请求序列化、缓存断点和有效期。[OpenAI 缓存规则](https://developers.openai.com/api/docs/guides/prompt-caching)、[Claude 缓存规则](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

新用户任务开始时移动快照也会改变请求前缀。例如：

```text
请求 1：系统 + 历史 H + 文档 V1 + 用户 U1
请求 2：系统 + 历史 H + 用户 U1 + 回复 A1 + 文档 V2 + 用户 U2
共同前缀：系统 + 历史 H
```

新增的 U1 和 A1 曾位于旧快照之后，不能因为它们现在成为历史就认定可以直接复用旧缓存。文件没有变化时，每个新用户任务都移动快照也可能减少该文档段的缓存复用；同一任务中的工具续轮不移动或替换快照。

实现时分别验证任务内部追加请求，以及任务之间替换基线并省略上一任务正文的缓存边界，记录实际缓存读取量。只有新任务边界才生成新的省略范围，同一任务不反复改写历史。保持系统提示、工具定义、消息顺序和序列化稳定，避免在请求前部加入每次变化的字段。具体缓存适配方案保留为实现决策。

## 文件编辑流程

### agent 的工作方式

agent 从快照中获得任务开始时的文件全文，主要使用编辑工具完成生成、替换和其他受支持的文件操作。任务中的后续状态由成功工具调用及结果表达，明确失败的操作不能当作已经生效。工具成功后返回简短结果，最终汇报说明改了哪些文件、主要改动和仍需处理的事项。

读取工具仍可用于目录外资料，以及任务中对最新正文的局部核对。读取托管文件时返回最新工作内存，不返回冻结的基线内容；如果已有工具记录足够理解变化，则不必重复读取全文。

使用专用文档工具，还是覆盖并转发 Pi 的内置文件工具，尚未确定。两种方式都必须让托管文件的成功变更经过统一状态管理，避免文件已修改而内存仍停留在旧版。

### 一次成功编辑

1. 校验目标路径属于托管范围，并核对编辑所依据的版本或内容。
2. 串行应用相关修改，生成候选文件状态。
3. 持久化恢复所需的内容和操作信息，并保存托管文件。
4. 在内存中发布新的当前工作区状态。
5. 返回足够表达本次修改的简短结果；下一次模型请求保留原全文基线，只追加工具调用及结果。

任务最终结束时保存最新工作区检查点和完整工具记录。下一条用户指令开始处理时，才用该工作状态更新全文快照，并在模型投影中省略上一已完成任务的重复工具正文。

编辑操作采用何种事务或恢复日志实现尚未确定，但成功返回必须意味着磁盘与工作内存一致，且模型可见的修改记录能够解释工作状态的变化。失败时回滚未确认修改或暂停任务并保留恢复依据，不能只返回成功提示。

文件清单应能够表达创建和删除；重命名是否作为独立工具操作属于接口决策。仅还原旧文件的正文不足以恢复整个工作区。

### 外部修改

自动比较只有三类检查点：新任务开始前、托管文件修改提交前、整个任务结束前。启动检查只在首次模型请求前执行一次，通过后才创建任务基线；同一任务的续答和补充指令不重复比较。实际树恢复属于文件提交，整批写入前比较一次。输入只保存指令；只读工具、工具返回、轮次结束、树列表、会话离开/进入、status 和压缩不另做磁盘比较。写入后核对本次涉及文件的结果，不重新扫描全目录。比较对象始终是最后有效工作状态，不是任务冻结快照。

启动前发现差异：任务尚未开始，原文字和附件保存为草稿；执行 sync 接纳并记录外部修改，或执行 recover 撤销外部修改，原指令都回填输入框，发送后创建新任务。执行中发现差异：中断并保存未完成记录，sync 接纳外部版本，recover 恢复最新有效工作版本；两者都结束旧任务，等待新指令。助手已经成功的修改用 /tree 撤销。

不持续监听、不定时轮询；任务中的外部修改要等下一次文件提交前或整个任务结束时才发现，期间的纯模型续答继续使用原冻结基线。待处理时保留草稿及排队补充，不自动执行，不能绕过状态继续写文件或请求模型。

检测提示直接比较最后有效工作状态和本次已读取的磁盘快照，按路径列出新增、修改、删除、权限变化，以及内容与权限同时变化的文件。路径相对托管目录，文件名中的特殊字符转义显示，不输出文件正文。待处理检查点保存可选的检测版本引用 externalSnapshotId；会话恢复从不可变版本重建上次清单，明确标注为历史检测结果，不重新扫描磁盘。旧检查点缺少该引用时沿用原有待处理提示。sync 或 recover 成功后清除待处理引用。

## 检查点与文件快照

### 检查点粒度

用户通常按一次任务理解版本，例如“生成初稿”“补充案例”“调整结构”。建议将初始挂载状态和任务完成状态作为主要检查点，在树中提供容易识别的标签。

底层仍需记录成功的文件变更及其对应位置，处理中断、失败和任务内部多次工具调用。任务完成、失败或中断的状态需要明确区分。

检查点保存对应位置的最新工作状态。任务基线引用和工具历史投影状态另行记录，用于恢复该位置的上下文；不能因为全文快照冻结，就延迟保存真实文件版本或把任务开始时的正文当作任务完成结果。原始工具参数和结果始终保留，不能将精简视图作为唯一的恢复来源。

第一版优先支持完整任务边界的回退。Pi 原生树还包含用户消息、工具调用和其他中间节点，哪些节点允许直接恢复、如何限制不完整的调用边界，需要在实现前确定，不能默认任意节点都有同样完整的检查点。

### 快照存储

建议使用独立的本地存储保存快照，不要求用户工作目录本身是 Git 仓库：

- 内容对象按内容指纹保存，相同正文只存一份。
- 每个快照保存当时的文件清单。
- 会话路径上保存检查点引用和挂载配置。
- 历史快照及其管理目录不进入托管文件集合，也不占用模型上下文。

存储位置、内容指纹算法、保留策略尚未确定。第一版不自动清理仍被任何历史分支引用的正文。

恢复范围为整个托管工作区。托管范围之外的文件不因分支切换而被改动。

## 使用会话树恢复

### 分支语义

```text
C0 初始状态
 └─ C1 生成初稿
     ├─ C2 扩充案例
     │   └─ C3 调整章节顺序
     └─ C2′ 重新设计章节结构
```

从 C3 回到 C1 后，恢复 C1 的文件内容和会话上下文。继续输入产生 C2′，模型只接收当前路径 C0 → C1 → C2′ 上的历史，原来的 C2、C3 仍保存在树中，可再次切回。[Pi 会话分支](https://pi.dev/docs/latest/sessions)

这是一项分支切换操作，不沿旧路径追加一个“内容等于 C1”的恢复版本。第一版不以“保留后续全部聊天、仅回退文件”作为默认恢复方式。

### 目标节点的实际含义

Pi 选择用户消息时，会将活动位置移到该消息的父节点，并把指令文本放回编辑器。因此，选择“扩充案例”这条用户指令，通常代表回到执行它之前；选择任务完成检查点则代表执行完成之后。

插件必须根据实际落点查找快照，不能直接将界面中选中的条目 ID 当作恢复后的叶节点 ID。未找到有效快照或落点不满足恢复条件时，应明确报告原因并停止切换。

### 恢复过程

1. **进入切换状态**：确保当前任务已结束或已安全停止，暂停新的编辑和模型请求。
2. **保存离开状态**：检查外部修改和未记录变更，保存原分支的恢复依据。
3. **准备目标状态**：解析实际目标路径，读取工作区快照、任务基线引用、工具历史投影状态和配置，校验完整原始记录及文件内容齐全，计算文件差异。
4. **执行切换与恢复**：切换 Pi 的会话位置，恢复目标托管文件及内存状态。
5. **重建请求上下文**：从完整原始记录读取目标路径的历史，移除离开分支的文件快照和工具投影；按目标任务的基线、修改记录及省略范围恢复上下文。从检查点接受新指令时，再以恢复后的工作区生成唯一的新任务快照，并重新确定可省略的已完成工具正文。
6. **校验并恢复工作**：确认会话、内存和磁盘一致后，允许用户继续。

该流程是逻辑事务要求。具体在哪个事件阶段落盘，以及失败时如何补偿，需要结合 Pi 生命周期实现，不能假定一个事件处理器天然提供跨文件和会话的原子性。

### 恢复失败

目标快照损坏或缺失时，在改变文件和会话之前拒绝恢复。切换过程中发生部分失败时，利用离开状态撤销已执行步骤；若无法完整撤销，进入明确的待恢复状态，暂停 agent 对托管工作区的使用。

不能只依赖事件处理器抛出异常来阻止后续请求，因为 Pi 会报告部分扩展错误并继续运行。请求入口和编辑工具都需要检查插件是否处于可工作状态。

### 分支摘要

正常回退不自动将离开分支的摘要带入目标分支，否则已经放弃的操作仍会影响后续上下文。若 Pi 原生界面提供保留摘要的选项，第一版需使用无摘要的切换路径，或明确处理该选项与本模式的关系。

这里约束的是离开分支的摘要；当前路径上的历史仍按 Pi 的正常会话规则处理。

## Pi 扩展接入

下表记录可利用的接口及其实现职责，具体组合需要验证。

| 接入点 | 插件职责 |
| --- | --- |
| `session_start` | 从当前活动路径恢复挂载配置和快照引用，处理启动、恢复和重新加载 |
| `before_agent_start` | 关联已保存的待执行指令；基线创建延迟到首次请求检查通过后 |
| 自定义工具或内置工具覆盖 | 将托管文件修改接入统一状态管理 |
| `turn_end` | 关联已完成工具调用和实时工作区变更，保存必要的边界状态，保持任务基线冻结 |
| `agent_before_settle` 与 `agent_settled` | 区分可写入边界与最终通知，标记任务完成或中断后的稳定状态 |
| `context_with_system` | 每次请求只核对已知运行状态；新任务首次请求比较磁盘，通过后创建任务基线，随后仅应用固定投影，不覆盖原始记录 |
| `session_before_tree` | 校验实际目标、保存离开状态、准备恢复；不满足条件时取消切换 |
| `session_tree` | 根据切换后的实际活动路径同步文件及内存，完成校验 |
| `session_shutdown` | 释放目录所有权，保留可恢复状态 |

Pi 的 `context` 与 `context_with_system` 对系统消息的处理不同。请求变换需要保留系统提示和工具声明；选择接口时还要验证是否改变原有缓存前缀。[Pi 扩展接口](https://pi.dev/docs/latest/extensions)

Pi 支持通过工具结果的 `details`、非模型上下文的自定义条目和外部存储保存状态。检查点引用适合保存在会话路径中，正文适合保存在独立内容存储。重建时沿活动路径查找，不能扫描所有条目后取全局最新值。[会话文件格式](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/session-format.md)

`context_edit` 可改变某条消息对后续上下文的贡献，但它不会自行恢复磁盘文件，也不会自动把快照移动到新用户指令之前。第一版是否使用它保存投影变化，保留为实现选择。

以下为计划验证的行为，尚未执行功能验证。

| 场景 | 预期结果 |
| --- | --- |
| 挂载目录 | 捕获初始工作状态，新用户任务开始时将其全文放入一条快照消息，文件排列稳定 |
| 连续修改同一文件 | 工作内存和磁盘随成功操作实时更新；同一任务各请求中的全文内容和位置保持不变 |
| 一次任务多次编辑 | 各次成功变更可恢复，模型通过追加的工具记录理解变化，任务完成检查点保存最终工作状态 |
| 任务内读取文件 | 返回最新工作内容，而非冻结基线 |
| 下一条用户指令开始 | 以最新工作状态替换唯一的全文快照，并在新任务中重新冻结 |
| 已完成的 edit 调用 | 下一任务投影省略旧文本和新文本，保留路径、调用 ID、执行结果及原始记录引用 |
| 已完成的 write 调用 | 下一任务投影省略正文；新基线承接最终文件状态，原始完整参数不变 |
| 当前任务工具调用 | 正文参数完整保留，不因某次调用成功就立即省略 |
| 混合 assistant 消息 | 只省略符合条件的工具正文，不改普通文字或其他工具参数 |
| 失败或未完成任务 | 保留继续判断所需的完整参数，不自动视为已被新基线承接 |
| 任务内重复构建请求 | 已有正文省略标记和范围稳定，原始消息不会被多次删除或改写 |
| 新基线建立失败 | 不发布缺少正文且没有有效新基线的模型视图 |
| 创建或删除文件 | 实时文件清单、磁盘和工作区版本一致；变化由成功工具记录表达，任务内冻结全文不变 |
| 工具执行失败 | 不将失败操作视为已生效；回滚未确认修改或暂停任务恢复 |
| 正常聊天 | 不自动提取要求，不删除普通聊天；仅在模型投影中按规则省略已完成工具正文，原始工具记录完整 |
| 回到初稿检查点 | 磁盘与内存恢复为初稿，后续路线消息不进入上下文，新任务以初稿建立冻结基线 |
| 从初稿另开路线 | 新路线使用初稿状态，旧路线仍可切回 |
| 切回原路线 | 恢复原路线关联的全部托管文件及聊天路径 |
| 回到工具压缩之前 | 从原始记录恢复当时完整参数，不继承未来任务的正文省略范围 |
| 选择用户指令 | 按实际执行前落点恢复，编辑器中的待提交文本不会被当作已执行任务 |
| 中断编辑 | 已成功的变更保留恢复依据，不将未完成任务标记为完整检查点 |
| 外部编辑后切换 | 外部修改先被保存，避免被静默覆盖 |
| 缺失快照或恢复写入失败 | 阻止继续使用不一致的工作区，并提供明确错误 |
| 退出重启或重新加载 | 活动路径和文件版本关联仍可恢复，历史快照可读取 |
| 上下文容量不足 | 明确报告容量问题，不静默丢弃托管文件正文 |
| 任务中发生历史压缩 | 保留解释当前工作状态所需的修改记录；不能保留时以最新工作状态显式重建基线 |
| 缓存观察 | 分别验证任务内冻结全文和投影，以及任务间替换全文并压缩工具正文的缓存读取量 |

## 实现细节建议

以下是针对待定问题的推荐方案，尚未作为已确认决定，也不代表功能已完成验证。前面的范围约定保持不变。

| 问题 | 第一版建议 | 主要理由 |
| --- | --- | --- |
| 命令与托管范围 | 一个 `/inmem` 命令入口、单目录、UTF-8 文本、显式容量预算 | 先把完整编辑和恢复闭环做稳定 |
| 文件工具 | 覆盖并复用 `read`、`edit`、`write`，托管文件经过统一状态管理 | 保留 Pi 已有工具习惯，减少重复实现编辑算法 |
| 检查点 | 每次完整工具轮次保存恢复信息，最终任务完成才标记用户检查点 | 同时满足中断恢复和用户按任务回退的习惯 |
| 消息构造 | 请求时注入任务内冻结的 `custom` 消息，使用 `context_with_system` 保留历史结构 | 不将每份全文追加到聊天，也不折叠原有系统消息 |
| 工具消息投影 | 按已确认规则，在新任务开始时确定 edit/write 的正文省略范围，原始记录完整保留 | 避免新全文与上一任务完整参数重复，并支持历史恢复 |
| 快照持久化 | 项目本地内容对象、文件清单、检查点引用、恢复日志 | 支持去重、删除恢复和跨进程继续工作 |
| 外部编辑 | 三类检查点；sync 接纳或 recover 撤销外部修改，旧任务结束 | 不监听，保留草稿和成功修改，助手修改由 tree 回退 |
| 缓存 | 任务内保护冻结全文和追加历史，任务间保护全文之前的稳定历史 | 减少工具续轮重复处理全文，分别验证两类请求的缓存边界 |
| 会话切换 | 保留原生 `/tree`，校验实际落点，无摘要切换 | 继续使用已有会话树，防止文件与消息错配 |

### 命令和托管范围

建议提供以下命令。名称是接口建议，不表示当前已可执行：

```text
/inmem on [directory]             在新会话首次聊天前创建 InMemory，省略目录时使用当前工作目录
/inmem status                     查看目录、文件数、快照和运行状态
/inmem sync                       接纳外部修改并记录消息，等待新指令
/inmem recover                    撤销外部修改，保留助手成功修改，等待新指令
/tree                              使用 Pi 原生会话树切换路线
/new                               新建会话，需要普通聊天或其他托管目录时使用
/resume                            选择已有会话，InMemory 类别显示固定标记
```

第一版一次管理一个目录，不先支持多目录拼接。会话类别和托管目录创建后固定，拒绝 `/inmem off` 和重复绑定。`/tree` 只允许有 InMemory 文件版本的位置，不能把专用会话变回普通类别。旧版普通位置及关闭点保留在原始历史中，但不出现在可选树里。

默认支持扩展名为 `.md`、`.txt`、`.json`、`.yaml`、`.yml` 和 `.toml` 的 UTF-8 普通文件。格式判断不负责解释 JSON 或 YAML 的业务结构，快照仍携带原始文本。其他文本类型通过显式包含规则开启。

建议默认排除 `.git`、`.pi`、`node_modules`、依赖和构建产物目录，以及账户配置等非文档内容。首次挂载列出纳入与排除的文件及原因。扩展名、隐藏文件和忽略规则采用明确配置，不默默改变托管范围。第一版不跟随符号链接；恢复时也重新校验路径，防止路径已经指向目录之外。

建议初始上限为 100 个文件、单文件 256 KiB、总正文 1 MiB，并允许配置调整。这些数值是资源上限起点，不能代替模型容量校验。快照 token 预算另建议设为 `min(32768, 模型上下文窗口的 25%)`；每次请求还要估算系统提示、工具、聊天、快照和输出预留的总量，超过预算则停止该次请求并说明原因，不截断正文。

无法准确分词时显示“估算”，使用保守估计和余量。模型尚未选定时可以完成文件扫描，实际请求必须等到模型容量明确。除已确认的完成任务工具正文省略规则外，不为容纳快照自动整理用户要求或主动删减普通聊天。

### 文件工具与修改入口

建议保留 Pi 的 `read`、`edit`、`write` 名称和基本参数。托管范围内使用插件状态管理；范围外转发给标准工具。Pi 已导出工具定义和可替换的文件操作接口，能够复用现有编辑匹配、换行处理和结果展示。

具体约定如下：

- `read` 读取已校验的内存内容，保留用户明确要求读取文件的能力。
- `edit` 复用标准文本编辑逻辑，通过自定义读写操作形成候选状态，统一提交工作区版本和磁盘写入，保留本任务的冻结基线。
- `write` 用于创建文件或整体重写，通过相同的提交路径处理。
- 删除和重命名使用小型 `memory_delete`、`memory_move` 工具，复用同一状态管理器；重命名同时检查源路径和目标路径。
- 托管工作区的修改串行执行，版本管理、外部同步和分支恢复也使用同一工作区锁。

工作区锁与标准工具的文件写入队列保持固定的获取顺序，避免在自定义文件操作中再次等待同一文件队列而造成死锁。

工具返回简短的变更说明，并确保模型可见的工具参数和结果足以表达实际生效的修改。差异、工作区快照 ID 和恢复信息可另存于结果 `details` 或外部记录中，但模型理解变化所必需的信息不能仅放在不可见的 `details` 里。若标准编辑产生与请求不同的实际修改，返回必要的实际差异；无需重复输出整篇正文。保留原有必要的渲染信息，避免覆盖工具自身的 `details`。

第一版不增加模型必须填写的版本号参数。编辑前核对磁盘内容是否仍匹配当前工作区快照，并在锁内完成修改；局部编辑继续要求旧文本匹配。外部冲突一旦出现，停止基于旧状态的写入，再用新的工作状态重新开始任务。

通过提示和工具描述引导 agent 使用托管工具修改文档。不能靠分析任意 `bash` 命令证明它没有写文件，因此还要校验工具前后的磁盘状态。通过 shell 或其他扩展完成的修改按外部变更保存；检测只能缩小竞态窗口，不能替代操作系统级文件隔离。

### 检查点写入和树中显示

建议分为两层记录：

1. **恢复记录**：每次成功的文件变更都有不可变快照；完整工具轮次结束后，将状态引用与该轮工具结果或边界条目关联。
2. **任务检查点**：初始挂载、任务最终结束和显式同步形成用户容易理解的恢复点。

撤销外部修改的 recover 只回到已有有效工作状态，不新增独立的“恢复完成”检查点。清除待处理标记和完成日志仍需持久化，使用隐藏的后台位置记录；旧版 recovery 条目保留原始数据，但不参与树选择，后代节点重新连接到最近的可见祖先。

`turn_end` 已位于 assistant 消息和本轮工具结果持久化之后，适合保存轮次状态。`agent_before_settle` 可以产生候选检查点；只有 `agent_settled` 确认任务不再自动继续后，才把候选标记为完成，并加上树中标签。失败和中断可以有“未完成”的恢复点，不能标记为成功完成。

Pi 默认的 `/tree` 过滤器会隐藏 `custom` 状态条目，即便条目有标签也不会自动出现在默认视图。因此，任务标签应挂到最后一条可见的 assistant 汇报上，例如“初稿完成”或“调整章节后”；不能只给隐藏状态条目起名。

恢复记录需要显式保存 `sessionId`、`anchorEntryId`、`workingSnapshotId`、`baselineSnapshotId`、`taskId`、用户指令锚点、配置引用、工具历史投影引用和状态。以 `sessionId + anchorEntryId` 建立精确索引，解决检查点元数据写在最终汇报之后、选择汇报本身时祖先路径尚不包含该元数据的问题。完成检查点的工作区引用指向最终结果，基线引用保留该任务的起点。索引是可重建的辅助数据，恢复时还要校验对应会话条目和记录，不能取目录中全局最新快照。

工具历史投影建议记录规则版本、已处理任务 ID、来源消息及调用 ID、允许省略的字段路径、原始记录引用和承接最终状态的基线引用。只保存重建视图需要的元数据；原始会话的工具参数和结果不做覆盖式压缩，也不保存脱离分支语义的全局“最新压缩状态”。

树中没有 assistant 汇报可供附加标签的初始或外部同步状态，可保留带标签的状态条目，通过 `labeled-only` 过滤查看。第一版不替换原生树界面。

允许的恢复落点建议先限定为：已建立索引的任务检查点、已记录的初始或外部同步点，以及父节点可解析为稳定检查点的用户指令。拒绝停在未配对工具调用中间，也不自动将用户选中的节点移动到别处。后续需要支持任意中间节点时，再扩展恢复映射。

### 快照消息和用户指令锚点

建议使用请求时的 `custom` 消息，类型固定为 `inmemory.workspace`，不将它通过 `sendMessage` 每次追加到持久聊天。消息由任务开始时保存的基线生成；工作内存改变后，同一任务仍注入相同正文和稳定的消息元数据。`details` 只携带插件识别信息。Pi 会将 `custom` 转换成模型可接收的用户数据消息，因此不能假设模型服务看得到独立的 custom 角色。

正文建议为一个有稳定说明头的内容块，加上按路径排序的文件内容块。说明头明确“本次任务开始时的文件状态，后续成功编辑以工具记录为准”。每个文件块编码路径、内容字节数和原文，用长度或明确转义规则消除正文与边界混淆。不要把整个文件正文 JSON 转义后反复展开，也不随意改动原文换行。同一任务内重复序列化必须得到相同结果，即使工作区已经变化。

采用 `context_with_system` 进行请求投影，保留既有系统消息、工具声明和消息顺序，对已完成任务应用固定的工具正文省略规则，再加入一个冻结的任务基线。所有修改仅作用于派生的请求消息，不直接改写原始对象。这样避免普通 `context` 变换在会话结构改变时将系统消息重新合并到开头。第一版不使用 `context_edit` 保存每轮文件全文，也不把每次进入投影事件当作新任务。

省略标记必须保持对应提供方接受的历史消息结构，不能删除仍需配对的调用、结果或擅改不透明的推理签名。具体字段替换需要与提供方协议一同验证；无法生成合法投影时保留原消息并报告未压缩，不能将损坏的消息作为成功压缩结果。

用户锚点从 Pi 尚未转换为模型角色的消息和会话条目识别。记录真实用户消息所在位置，而不是从已经将快照、摘要和 shell 输出都转换为 user 角色的请求中倒推。不要在 `message_end` 事件里直接把当前叶节点当成新消息 ID：本地版本在扩展处理该事件之后才持久化新消息。

空闲时的新用户指令实际开始处理后建立新的任务和快照锚点。排队的 follow-up 尚未执行时不预先替换快照。执行途中追加的 steering 指令需要明确归属于当前任务补充，还是另一个新任务，不能只因为出现了一条消息就自动替换全文；具体调度归属需要用真实事件序列做原型验证。

当前任务的补充指令只追加到已有基线后；若明确开始处理新的用户任务，则在工具调用与结果完整配对后，先保存离开状态，再以实时工作区捕获新基线。只有来源任务确已完成才压缩其正文；普通工具续轮、重试和自动继续均不建立新基线或提前精简本任务参数。

若历史压缩移除原指令或修改记录，不能继续使用缺少后续变化依据的旧基线。压缩后需保留足够的成功修改信息；无法保留时，在完整工具边界以最新工作状态显式建立新的上下文基线，记录这次恢复性重建，再在后续调用中冻结。该动作是压缩或恢复导致的例外，不是普通工具续轮的更新策略。优先验证任务完成后压缩的路径。

### 快照存储和恢复日志

建议存储于项目工作目录下的 `.pi/inmemory/<workspaceId>/`，其中 `workspaceId` 来自规范化挂载根目录的指纹。状态目录始终排除在托管文件集合之外。项目迁移后需要显式重新绑定根目录，不仅凭旧绝对路径写文件。

```text
.pi/inmemory/<workspaceId>/
  objects/          按 SHA-256 保存的原始文件字节
  manifests/        按路径排序的不可变文件清单
  checkpoints/      会话节点与快照的关联记录
  projections/      任务对应的工具正文省略范围和规则版本
  transactions/     未完成操作和恢复日志
  index.json        可以重建的检查点索引
```

文件内容按原始字节保存，以便准确恢复 UTF-8 BOM、换行和空文件；清单同时记录路径、内容指纹和必要的普通文件权限。文件清单有无某个路径，分别表达存在或删除。第一版不复制符号链接和完整文件系统元数据。

插件追加的管理条目仅保存引用和配置，Pi 原始会话仍完整保存工具调用参数及结果。正文对象先保存，引用后发布，防止检查点引用尚未持久化的内容。第一版不自动清理历史对象，也不要求 Git 仓库。

恢复日志建议记录 `prepared → files-applied → state-committed → done` 阶段，以及旧节点、实际目标节点、旧快照、目标快照和挂载配置。单文件通过同目录临时文件替换；多文件依靠日志、顺序执行和补偿恢复，不能将它称为整个目录的原子替换。

在 `session_before_tree` 中完成目标校验和日志准备，必要时返回取消；在 `session_tree` 中根据实际落点完成文件和内存同步。恢复失败后记录错误并暂停托管操作。需要切回原节点时，由后续用户命令在命令上下文执行，不能在生命周期事件里递归调用仅供命令使用的导航接口。

### 外部编辑和重新启动

比较只保留三类自动检查点，具体边界见“外部修改”。新建挂载需要捕获初始全文；显式 sync/recover 按用户选择读取、备份和处理磁盘。其余会话加载只恢复已知状态，不主动比较或覆盖当前文件；差异延迟到新任务开始前或实际文件提交前发现。

| 操作 | 任务尚未开始 | 任务执行中 |
| --- | --- | --- |
| `/inmem sync` | 接纳外部修改、记录修改消息；原指令回填输入框 | 接纳外部修改、记录修改消息；旧任务结束但未完成，等待新指令 |
| `/inmem recover` | 撤销外部修改；原指令回填输入框 | 撤销外部修改，保留成功工具修改；旧任务结束但未完成，等待新指令 |

例如 A 是任务开始状态、B 是助手最后成功状态、C 是外部修改：sync 保留 C，recover 恢复 B，回到 A 用 /tree。两个命令都不自动请求模型。中断任务保留完整工具正文，下一指令建立新任务和新冻结快照。

草稿元数据保存待提交文字、图片附件和尚未交付的补充。首次请求失败不创建任务，不更改上一已完成任务；处理后将未执行提交退回原位置并回填草稿，原始记录留在旧分支。执行中中断则保留当前路线和最新有效 workingId。已知 pendingExternal 和草稿会随重开会话恢复，文件碰巧被改回也不自动解除待处理状态。

同一托管目录第一版只允许一个写入会话。不同进程或多个会话同时管理同一目录时，使用按规范化根目录确定的共享锁检测冲突；只读检查仍可进行。当前进程内正常切换会话时转移所有权。重叠挂载目录也应检测，不能只比较目录字符串是否完全相同。

专用会话的运行状态有 `ready`、`switching` 和 `needs-recovery`，状态改变不影响其 InMemory 类别。普通会话不创建托管工作区。除 `ready` 外，阻止新的托管写入和依赖快照的模型请求；使用输入处理、显式取消和工具阻断实现，不能只靠抛出会被 Pi 捕获的异常。

### 缓存适配

建议核心模块只负责确定性的消息投影，模型适配层负责缓存标记，并在不支持时退回宿主原有行为。正确性不依赖缓存命中。

第一阶段记录实际发出的请求结构以及宿主报告的缓存读取量，只记录调试所需信息，正文不默认写入日志。同一任务内，缓存边界可以覆盖冻结全文、固定的工具历史投影、用户指令以及已追加的当前任务工具历史；跨任务时，对上一任务参数的省略会从首次改写处影响缓存。只在新任务边界确定一次省略范围，并保持更早已经精简的内容稳定。针对已验证的 API 设置适用边界，保留先前仍可复用的边界，不能每次只保留一个不断后移的新边界。

Claude 使用其支持的内容块缓存标记；OpenAI 则按具体 API 和模型支持的缓存选项处理，不能把 Claude 字段直接发送过去。相邻用户消息可能被提供方合并，因此定位应以实际序列化的内容块为准。变换通过 `before_provider_request` 进行时，只对可识别且已验证的负载结构生效，不在通用路径猜测字段。

本地 1.3.0 的 Claude 适配器会在末尾用户或系统消息的可缓存内容块上设置标记。冻结全文有利于任务内追加请求复用缓存，但任务之间替换全文时，该标记本身仍不能保证命中更早的稳定历史。因此，第一版应先完成一条提供方的两类请求缓存验证，再逐个扩展其他 API；不要承诺所有模型都已获得相同优化。

### 原生树和其他会话入口

保留 `/tree` 命令和原生选择器。`session_before_tree` 根据条目类型计算实际落点，再检查检查点、工具协议和目标文件；`session_tree` 使用事件提供的实际新叶节点二次核对。

本地 1.3.0 的切换前事件可以取消导航，但没有返回“关闭摘要”的字段；仅修改事件中的摘要意愿也不能假定会改变宿主导航选项。建议在模式涉及的切换中，遇到请求生成旧分支摘要时取消该次导航，并提示选择无摘要方式。

项目可以显式设置 `branchSummary.skipPrompt: true`，让原生树直接采用无摘要方式。插件不静默修改用户的全局设置，也不通过覆盖 `/tree` 重做整个界面。

`/new` 和 `/resume` 在离开时保存当前状态，在进入时识别新会话的固定类别并重建其工作区。没有 InMemory 记录的会话保持普通类别；不能把前一个会话的内存直接带过去。已有 InMemory 历史的会话即使停在旧版普通位置，也必须先恢复，不能继续普通聊天。`/reload` 恢复已知状态与草稿，磁盘比较延迟到新任务开始前或实际文件提交前。

第一版不扩展 `/fork` 的文件分支语义。InMemory 会话请求 fork 时，通过 `session_before_fork` 取消并解释第一版请使用 `/tree`，包括待恢复状态；普通会话仍使用 Pi 原有 fork 行为。该限制属于本版接口范围，不意味着 Pi 自身不支持 fork。

### 建议的实现顺序

1. **先验证宿主接入**：用无模型的原型确认带摘要导航的取消、实际落点、可见标签、事件持久化顺序，以及错误状态能否真正阻止提供方请求。
2. **实现文件状态与请求投影**：完成单目录挂载、标准工具覆盖、工作内存与磁盘实时同步；验证任务内全文冻结，以及下一任务开始时替换全文并省略已完成工具正文。
3. **实现检查点与树恢复**：覆盖回退、另开路线、切回、完整原始参数与对应投影的恢复，以及创建删除、中断和崩溃恢复。
4. **补齐外部同步和缓存适配**：验证执行中追加指令、压缩后的快照位置，再用真实提供方请求观察缓存。

进入完整实现前，最需要验证的三项是：最终汇报与检查点的精确关联、执行中追加指令的插入边界、恢复失败后的请求取消。如果公开扩展接口无法满足其中某项，应先报告具体缺口，再决定是否提出最小宿主改动，不通过私有字段绕过生命周期。
