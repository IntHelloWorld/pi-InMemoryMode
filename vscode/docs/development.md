# VS Code companion development guide

## Responsibilities

The root Pi plugin owns sessions, file versions, frozen task baselines, external-change checks and recovery. The VS Code extension owns terminal launch, file decorations, the sidebar, diff presentation and selection sharing.

| File | Responsibility |
| --- | --- |
| Root `src/ide-protocol.ts` | Shared plain types and request validation |
| Root `src/ide-bridge.ts` | Local Pi bridge, command dispatch and receipts |
| Root `src/controller.ts`, `src/drafts.ts` | Mounting, version decisions and draft restoration |
| Root `tests/ide-bridge.test.ts` | Bridge and file behavior through the real Pi SDK |
| `src/client.ts` | Connection discovery and loopback HTTP client |
| `src/sessions.ts` | Session selection and state refresh |
| `src/model.ts` | Path scope, selection formatting and decoration rules |
| `src/launcher.ts` | Pi/Node discovery and GUI terminal PATH |
| `src/logging.ts` | Output logging interface |
| `src/views.ts` | Native tree, file decorations and immutable diff documents |
| `src/review.ts` | Automatic review and Continue/Recover coordination |
| `src/extension.ts` | Commands, context keys, status items and terminals |
| `scripts/`, `tests/` | Build, functional tests and real extension-host verification |

The root Pi source package imports the protocol directly. The VS Code build bundles it into `dist/extension.cjs`; the installed VSIX does not depend on parent source files, development dependencies or a separate background service. The root Pi package excludes the VS Code subproject.

## Language and command names

Use English for all product text: commands, descriptions, tooltips, dialogs, notifications, status items, logs, tool descriptions, model-facing metadata and selection wrappers. Preserve selected bytes, user filenames and user-defined names. Explicitly format extension-owned inspection timestamps in English. Translate only the known labels generated by old plugin releases when displaying the tree; never rewrite raw session history.

The public Pi namespace is `/inmem`: `on [directory]`, `status`, `check`, `sync`, `recover`. Do not register `/memory` aliases, which would continue to conflict with other plugins. The authenticated internal entry point is `/inmem-ide <id>`. Persistent `inmemory.*` metadata, storage paths and existing tool IDs remain compatible with saved sessions. Test command coexistence by loading another plugin that owns `/memory` and exercising both routes through the real Pi SDK.

## Setup and debugging

At the repository root, run `npm ci --ignore-scripts` and `npm run setup:tree`. Then, in `vscode/`:

```bash
npm ci --ignore-scripts
npm run check
npm run build
npm test
```

Open **the `vscode/` directory itself** and press F5 to launch the extension development window. Build tasks and launch configuration are included. Use `npm run watch` while editing, then reload the development window.

Set `piInMemory.pluginPath` to the repository root in the development window’s user settings. Set an absolute `piInMemory.executable` path when needed. The root development dependency uses the local UI patch; global Pi must be patched separately.

This version supports local desktop workspaces. Keep session history navigation in the Pi terminal with `/tree`. Each InMemory session mounts one directory; the folder context command starts a new session.

## Connection discovery

At TUI startup, Pi binds an HTTP server to a random port on `127.0.0.1` and writes a descriptor under the system temporary directory’s `pi-inmemory-ide-<uid>/`. `PI_INMEMORY_IDE_DIR` selects an isolated test directory. Non-TUI sessions normally do not start a bridge; the test directory allows SDK integration tests to enable it.

The directory uses mode `0700`, descriptors `0600`. A descriptor contains the protocol version, random instance ID, PID, port, access token, working directory and optional terminal ID, without file content. Requests require a Bearer token and reject browser Origin headers. Never copy descriptors or tokens into docs or logs.

Every 1.5 seconds, VS Code discovers live connections in the project scope and reads existing state. A dead process or failed connection removes active markings. Normal shutdown deletes the descriptor; stale descriptors from crashes are ignored after process/connection validation. Users select among multiple connections; decorations, actions and status follow that selection.

## Request protocol

- `GET /state` reads current state and existing immutable snapshots without scanning managed files.
- `POST /command` includes `id`, `sessionId`, `leafId` and `action`. Supported actions are `mount`, `check`, `sync`, `recover`, `selection`, `diff`, `diffs`.
- Identical retries reuse recent results; reusing an ID with different content is rejected. The last 100 receipts are kept within the instance, without a cross-process exactly-once guarantee.
- Actions validate the target session and position. Mount, check and version decisions require Pi to be idle. IDE operations execute serially.
- Dispatch uses `pi.sendUserMessage('/inmem-ide <id>', {expandPromptTemplates: true})` to obtain an official extension command context. The command resolves a previously validated request ID; it does not parse terminal output or simulate keystrokes.
- Normal selections use `expandPromptTemplates: false` and follow the existing input/task/snapshot lifecycle. `submitted` confirms delivery to Pi; the terminal shows model execution results.
- A busy session, pending recovery or existing draft keeps a selection as a draft, without interrupting the task or starting another model request.

## File checks and diff editors

Paths are relative to the mount. `workingId` identifies the last accepted version; `externalSnapshotId` identifies the last inspected disk snapshot.

`diff` reads one file and `diffs` reads all pending files from those immutable versions, rejecting unknown or out-of-scope paths. Neither scans disk. Existence and permissions are separate fields.

The original side uses a read-only snapshot document. Existing regular files on the modified side use their real file URI and are editable; deleted or unreadable files fall back to the inspected read-only version. Added files have an empty original. All diffs open through the public [`vscode.changes`](https://code.visualstudio.com/api/references/commands) command in a native changes editor.

`vscode.changes` creates a fresh input on every call. A stable per-session title, including a short identifier to distinguish same-named directories, finds the existing editor. A resource signature decides whether it needs refreshing. Unchanged resources only focus that editor through built-in navigation commands; concurrent requests are coalesced. Read-only URIs depend on the path, existence and content, also allowing single-file editor reuse. Before replacing a changed resource list, pin dirty files in ordinary editors to retain buffers and undo history. This neither saves, accepts nor reverts file contents. Pin the changes editor itself so opening another file cannot replace it as a preview. Production code neither reads proposed multi-diff Tab inputs nor calls a private multi-diff opening command; host tests may inspect native Tab resources for verification.

The selected session automatically opens all diffs once per pending stage. Polling does not repeatedly steal focus. `autoOpenChanges` controls this behavior; `diffAll` always allows a manual open. Completed decisions close review pages without dirty edits.

Recover visibility depends on the pending Pi state, not buffer dirtiness, file count or whether edits were saved. Both actions have fixed text rows in the sidebar and editor context menu entries; the status bar also exposes Pi: Recover. This keeps Recover available even when toolbar icons overflow.

Continue maps to `sync`; it is not a new Pi terminal command. It saves dirty managed files, checks the current disk version and asks to accept the entire directory. Recover checks, confirms, reverts dirty managed documents through VS Code and asks Pi to restore the last accepted version. Cancelling Recover keeps buffers and disk unchanged. Files outside the known managed/pending lists are not automatically saved or reverted.

`sync` and `recover` carry the reviewed version IDs. A later state or disk change rejects the decision and refreshes the list. VS Code does not write the version store; recovery and file mutations remain in Pi’s existing serialized workspace queue. Both decisions restore the pending instruction for explicit resubmission, without running the model.

`check` records pending changes without accepting content. A later disk reversion to identical bytes does not silently clear the pending decision. Unsafe or unreadable disk states retain the existing recovery requirements.

## Terminal association

Launch Pi directly with `TerminalOptions.shellPath/shellArgs`, passing each argument separately. Pi’s `#!/usr/bin/env node` requires Node on the terminal PATH. Resolve executable Pi and Node first: use configured `nodeExecutable`, then Pi’s directory, PATH and common install locations. Explicitly add the resolved directories to PATH. GUI VS Code may not inherit a login shell’s environment, and Electron’s `process.execPath` must not be used as Node. Fail clearly before terminal creation if the runtime cannot be found.

`PI_INMEMORY_TERMINAL_ID` associates a terminal; `PI_INMEMORY_MOUNT` supplies the initial mount. Startup waits for both the connection and mount acknowledgement.

Manually launched Pi sessions are discoverable too. A general shell terminal’s children cannot reliably be inferred, so users associate a terminal when focusing a manual session. Text and actions always go to the selected Pi connection.

## Output logs

Use the native `LogOutputChannel` named `Pi InMemory`, with timestamps and levels. `piInMemory.showLogs`, the sidebar button and the error notification’s **Show Logs** action expose it.

Log the version, working directories, resolved Pi/Node paths, connection changes, state transitions, action types and results. Never log tokens, authorization headers, full requests, selection/file content or extra startup argument values that could contain secrets. Unchanged polls are silent; identical connection errors are coalesced, with a separate restoration entry.

## Verification

At the repository root, run `npm run check`, `npm test` and `npm run smoke`. In this subproject:

```bash
npm run check
npm test
npm run build
npm run test:host
npm run package
```

`test:host` prefers the installed macOS VS Code. Set `VSCODE_EXECUTABLE` to override it; otherwise the official test runner can download VS Code. Tests isolate the user profile, extensions, workspace, Pi configuration and connection directory, clean up afterwards and do not alter personal settings or call a real model.

- Root bridge tests exercise the real Pi SDK: mounting, authentication, retries, stale requests, checks, recovery, diffs and drafts.
- Unit tests cover managed scope, ancestor decorations, exclusions and exact selection-content preservation, including non-English input.
- Real VS Code host tests cover commands, Output, selection forwarding, automatic and reusable reviews, repeated/concurrent clicks, cross-group focus, reopening with the original baseline, dirty-buffer retention on file-list changes, Continue, cancelled/confirmed Recover, real terminal mounting and exit. Only human confirmation is injected; files and editors are real. The terminal runs the actual Pi shebang with a minimal GUI PATH, without bypassing it through Node. `PI_IDE_TEST_PI` can select a global Pi. On failure the isolated extension logs are printed before cleanup.
- Deterministic model replies do not demonstrate provider cache hit rates, paid model behavior or every platform/theme.

Manual acceptance should also cover light/dark decorations, session switching, existing input drafts, Unicode and spaced paths, permission changes, failed saves/reverts, and marking updates after `/resume` and `/tree`.

## Packaging

`npm run package` produces a local VSIX without publishing it. Include the compiled extension, icon, README, development guide and license; exclude source, tests, dependencies, source maps and temporary data.

Change both sides, functional tests and this guide together when modifying the protocol. Increase the protocol version for incompatible wire changes.
